# Data Model Contract

## Database Rules

- PostgreSQL is the system of record.
- Drizzle schema definitions and checked-in migrations are authoritative.
- Primary keys are UUIDs generated by PostgreSQL or Drizzle's PostgreSQL UUID default.
- Timestamps use `timestamptz` and represent UTC instants.
- Calendar-only dates use PostgreSQL `date` and API `YYYY-MM-DD` strings.
- Currency uses PostgreSQL `numeric(12,2)` and decimal strings in TypeScript/API boundaries.
- Estimated hours use `numeric(8,2)` and decimal strings.
- JavaScript floating-point arithmetic must not determine stored currency values.
- Every mutable entity has `created_at` and `updated_at`; immutable history records have `created_at`.
- Foreign keys and database checks enforce structural integrity.
- Hard-delete APIs are out of scope. Foreign-key deletion should default to `RESTRICT` unless a reviewed retention decision says otherwise.
- Migrations must not use destructive reset or push behavior against shared environments.

## Tenant Ownership

The client organization is the tenant owner of a project.

```text
Organization
  -> Project
    -> ChangeRequest
      -> Estimate
      -> Comment
      -> StatusHistory
      -> TimeEntry
      -> Attachment
```

Child tables do not duplicate `organization_id` in P001. Tenant scope is resolved through the project relationship and enforced by service authorization plus scoped repository queries.

| Column          | Type              | Rules                                       |
| --------------- | ----------------- | ------------------------------------------- |
| id              | uuid              | primary key                                 |

| organization_id | uuid              | required, FK organizations, restrict delete |

### organization_invitations

| Column             | Type              | Rules                                       |
| ------------------ | ----------------- | ------------------------------------------- |
| id                 | uuid              | primary key                                 |
| organization_id    | uuid              | required, FK organizations, restrict delete |
| invited_user_id    | uuid              | required, FK users, restrict delete         |
| email              | varchar(320)      | required, lowercase                         |
| proposed_role      | organization_role | required                                    |
| invited_by_user_id | uuid              | required, FK users, restrict delete         |
| authorized_by_role | organization_role | required authorization snapshot             |
| status             | invitation_status | required, default `PENDING`                 |
| token_hash         | varchar(64)       | required, unique SHA-256 digest             |
| expires_at         | timestamptz       | required                                    |
| accepted_at        | timestamptz       | nullable                                    |
| revoked_at         | timestamptz       | nullable                                    |
| resent_at          | timestamptz       | nullable                                    |
| resend_count       | integer           | required, default 0, non-negative           |
| created_at         | timestamptz       | required                                    |
| updated_at         | timestamptz       | required                                    |

Constraints and indexes:

- one pending row per `(organization_id, email)` through a partial unique index;
- unique token hash;
- organization/newest-first and invited-user indexes;
- expiry is seven days from create or resend;
- plaintext token material is never persisted.

`authorized_by_role` records the inviter role that passed the role ceiling when
the token was issued. An authorized resend replaces both `invited_by_user_id`
and this role snapshot with the resending administrator's identity and current
role. Acceptance evaluates the proposed role and any current suspended target
membership role against this immutable token-generation snapshot, so later
inviter suspension or demotion neither weakens the ceiling nor silently voids
an already authorized token.

## Transaction Rules

Use a transaction when one use case changes multiple related records.

P001 required transaction:

```text
insert change_request
insert initial status_history
commit together or roll back together
```

Future estimate approval and status transitions will require similar transactions.

P002 additionally requires one transaction for every access mutation:

- invitation create/resend/revoke plus its audit event;
- invitation acceptance, user activation, membership create/reactivation, invitation acceptance, and audit event;
- membership role/status update plus its audit event.

Invitation acceptance locks the token row so concurrent attempts produce at most one success. Membership changes use a tenant-scoped transaction lock and `expectedUpdatedAt` optimistic state check.

## Seed Contract

Seed data must include:

- one `INTERNAL` AppSolo organization;
- one `CLIENT` organization;
- one AppSolo owner;
- one AppSolo developer;
- one client administrator;
- one client member;
- internal memberships for AppSolo users;
- scoped client-organization memberships for the internal users who support the project;
- client memberships for client users;
- one active project;
- several change requests in different statuses;
- at least one estimate using exact decimal strings;
- client-visible and internal-only comments;
- several status-history records.

Use clearly fake addresses under a reserved or obviously local domain, for example `owner@appsolo.test` and `admin@client.test`.

Seed execution must be idempotent or must fail with a clear reset instruction. It must not silently duplicate records on every run.

P002 adds a suspended membership, an invited user, a pending invitation with no usable committed bearer token, and a matching audit event. These fixtures remain clearly fake and deterministic.
